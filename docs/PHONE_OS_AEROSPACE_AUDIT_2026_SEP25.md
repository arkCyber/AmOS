## 0. 审计方法与判据

本次审计不采信"函数存在"，只认**已接线且可达**。四类判据：

1. **真实实现**：功能是否最终触达平台 API / 真实网络，mock 是否可能在生产被启用而不被披露。
2. **闭环完整**：链路每一环（拨号→通话→录音→挂断；发→回执→收件箱；连接→认证→拉取→阅读→发送）是否接线，断在哪一环。
3. **错误处理**：每个可失败操作的结果是否 (a) 返回、(b) 被调用方检查、(c) 被静默丢弃。特别扫描：忽略的 `Result`/`bool`、`unwrap/expect`、错误折成默认值、**被拒却报成功**、JNI 吞异常。
4. **一致性**：同一规则是否只有一个真相源，姊妹路径是否漂移（本仓高频缺陷族）。

## 1. 总体结论矩阵

| 功能域 | 真实实现 | 错误处理 | 闭环完整性 | 一句话结论 |
|---|---|---|---|---|
| 电话 | PARTIAL | 良好 | 在录音处断裂 | 真机拨号/呼入诚真；守护进程恒为 mock；录音诚实拒绝（能力缺失） |

### PH-P0-1 · 邮件生产环境是 mock，却向用户报「已发送」（诚信）

**现象**：无账号启动即注入两封演示邮件；点发送后界面显示「已发送」，实际从未触网。

**证据**：
- `crates/amos-tauri/src/mail.rs:62` —— `MailBridge { client: MailClient<MockMailProvider> }`，类型硬编码为 mock。
- `crates/amos-tauri/Cargo.toml:23` —— 依赖 `amos-mail` 未启用 `live` feature；全仓无运行时切换路径（无账号配置命令、无环境变量选 live）。
- `mail.rs:114-127` —— 无 `$AMOS_MAIL_STORE` 时 `seeded()` 注入 2 封演示邮件。
- `frontend-ts/src/svelte/MailApp.svelte:611-615` —— 渲染「已发送」；`MailApp.svelte:65` `online = bridged()`，只表示"宿主存在"，从不表示"真实网络"。

**建议修复**：(a) 最小——在 UI 与 `mail_status` 增加"演示模式（未配置账号）"的显式标识，发送回执前缀 `local/` 以示未投递；(b) 完整——新增 IMAP+SMTP 组合 provider，由账号配置选择，未配置时**拒绝发送**而非假成功。

### PH-P0-2 · 短信三项权限"只检查、从不申请"，真机安装即功能不可达

**证据**：
- `android-glue/com/amos/ai/glue/SmsGlue.kt:53,207,254,298,353` —— 仅 `checkSelfPermission`。
- 全仓 `grep` 无任何 `requestPermissions(READ_SMS / SEND_SMS / RECEIVE_SMS)` 调用；对照 `MicPermissionGlue.kt:82`、`TelephonyGlue.kt:235` 均有申请路径。
- `android-glue/.../AmosGlue.kt:63` 注释自认"授权后生效（调用时检查）"——但**没有任何代码负责去授权**。
- `docs/sms.md:47` 唯一证据是 `adb install -g`。

**影响**：非 debug 安装下收件箱永久报权限错、`SmsReceiver` 永不投递——"存在"与"可达"完全背离。

**建议修复**：仿 `MicPermissionGlue` 增加 `SmsPermissionGlue.request(...)`，在信息应用首次进入时申请；拒绝时界面给出可行动指引。

**验收**：新增申请路径的单测/仪器测试；`scripts/android-permission-scan.mjs` 能识别 READ_SMS 的申请站点。

**状态：已修复（2026-09-25，REQ-A1577 ∕ F-TEL-037）**。仿 `MicPermissionGlue` 新增整条申请缝：Kotlin `SmsPermissionGlue`（`object`，`bind` ∕ `onResult(Boolean)` 两个 `external fun`，`REQ_SMS=9005`，`ensureBound` ∕ `allGranted` ∕ `request` ∕ `onSmsResult`）经 `ActivityCompat.requestPermissions` 弹系统对话框；`MainActivity.onRequestPermissionsResult` → `PermissionWire.REQ_SMS` → `onSmsResult` 回填 Rust 侧 `sms_permission.rs` 的 `oneshot`（`GRANT_TIMEOUT=30s`）。设计上：三个权限作**一个集合**申请（部分授予折成 `denied`，与「三权限是一件事」一致）；判定**回读平台**（`allGranted()`）而不是折 `grantResults` 的顺序（后者在混合授予时对每一项都判错）。前端 `lib/smsPermission.ts::smsGrantRefusalKey` 把 granted ∕ denied ∕ timed-out ∕ unreadable ∕ host **五种回答分别说话**——只有 OS 自己的「否」才指向系统设置，超时∕读失败∕此环境无弹窗各有各的句子；`MessagesApp.svelte` 在读取被拒时给出可点的「授予短信权限」按钮。**证据 ∕ 负控**：`cargo test -p amos-tauri --lib sms_permission::` **9 ∕ 9**（含源码钉 `every_sms_permission_the_glue_checks_is_also_requested`：从 `SmsGlue.kt` 读出被检查的每个权限，断言申请缝都在申请、且 `MainActivity.Wiring` 把 `REQ_SMS` 路由到位）；`bun test src/__tests__/smsPermission.test.ts` **6 ∕ 6**；`vitest svelte-tests/messages-sms-grant.svelte.test.ts` **3 ∕ 3**（拒读出现按钮 ∕ 授予后按钮消失并画出会话 ∕ 超时说超时话、不含设置提示）；负控 4 条（删 `REQUIRED` 项 ∕ 删 `REQ_SMS` 路由分支 ⇒ 源码钉红；删主分支按钮 ⇒ 组件测试 3 ∕ 3 红；把 `grantSms` 折成一切非 granted 即 denied ⇒ **只有超时那条**红）。**边界**：真机系统弹窗的端到端行为只能设备时验证——host 编译 + 源码钉只覆盖结构（申请缝在、权限集一致、`REQ_SMS` 路由到位）；原拟 `REQ-A1570` 已被并发播客轮占用，让号至 `REQ-A1577`。

### PH-P0-3 · 短信发送"假成功"，失败时静默吞掉用户文本

**证据**：
- `SmsGlue.kt:366-368` —— `sendTextMessage(normalized, null, text, null, null)` 与 `sendMultipartTextMessage(..., null, null)`，`sentIntent` / `deliveryIntent` **均为 null**。
- 全仓无 `SMS_SENT` / `SMS_DELIVERED` 接收器（grep 0 命中）；仅"调用未抛异常"即 `{"ok":true}`（`SmsGlue.kt:370`）。
- 该 ok 变成 `"sent"`（`crates/amos-tauri/src/sms.rs:1102`）与 `smsSend` 的 boolean（`frontend-ts/src/lib/backend.ts:1928`）。
- UI 据此清空输入框（`MessagesApp.svelte:554`）且不设任何错误态。

**影响**：无信号/无服务时用户文字消失，无气泡、无错误、无投递状态——"拒绝报成功"。

**建议修复**：注册 `SMS_SENT`/`SMS_DELIVERED` `PendingIntent`，把结果回报到前端；发送态分"已提交/已送达/失败"三态，失败保留文本并可重试。

**验收**：失败发送不得清空输入框、不得显示成功；新增对立控制（发送被拒 → 可见错误）。

**状态：已修复（2026-09-25，REQ-A1620 ∕ F-TEL-040）**。①`SmsGlue.send` 不再传 `null` 状态意图：为**每一分段**注册 `SMS_SENT` `PendingIntent`（包内私有 action `com.amos.ai.glue.SMS_SENT` + `setPackage(自己的包)` + `FLAG_MUTABLE`）并注册一个 `NOT_EXPORTED` 动态接收器（广播以本应用身份发出，第三方伪造不了），`SendProbe` 等**全部**分段 —— 一段被拒即整条被拒；`SENT_WAIT_MS = 6000` 严格小于 Rust 的 `SMS_TIMEOUT = 8s`，慢电台落成 glue 自己的 `unconfirmed` 而不是调用方超时后丢掉原因。②`{"ok":true}` 这个形状被**删除**：每段 `RESULT_OK` 才 `{"state":"sent"}`，具名失败（`RADIO_OFF` ∕ `NO_SERVICE` ∕ `GENERIC_FAILURE` ∕ `NULL_PDU`）→ `{"error_kind":"rejected"}`（是错误），窗口内无结果 → `{"state":"unconfirmed","detail":…}`。③域内 `SmsSendOutcome { Sent, Unconfirmed(String) }` 替换 `Result<()>`，`parse_send_reply` 只认 `state`（修前那个被测试**钉成契约**的 `{"ok":true}` 断言按缺陷一并删掉）；`sms_send` 回 `outcome.wire()`，`smsSend` 回 `"sent" | "unconfirmed" | "failed"`。④UI 三态：只有 `sent` 才清空输入框并消费草稿；`failed` 保留文字 + 红色 `role="alert"`；`unconfirmed` **保留**输入框与草稿，用 `role="status"` 的琥珀色单独说「尚未收到发送结果：短信可能已发出，请勿重复发送。」。**验收达成**：被拒 ∕ 无结果都不清空输入框、都不显示成功（`vitest svelte-tests/messages-send-verdict.svelte.test.ts` **4 ∕ 4**），并有源码钉 + 三个负控。**如实边界**：不宣称 `SMS_DELIVERED`（网络回执可能几分钟才到，超出同步调用的窗口）；未做真机复核（只保证 `cargo check -p amos-sms --features android` 编译）。

### PH-P0-4 · 拦截规则前缀的"去零"绕过长度守卫，导致大面积误杀

**证据**：
- `crates/amos-blocklist/src/list.rs:101` —— `MIN_PREFIX_DIGITS = 3` 校验作用于**原始** digits。
- `crates/amos-blocklist/src/rule.rs:199-205` —— 匹配时 `starts_with_number` 先 `trim_zeros(prefix)`（`rule.rs:169-172`），剥掉前导 `0`/`00`。
- 于是合法输入的前缀规则 `"010"`（4 位，通过校验）实际生效为 `"10"`，会拦掉 `10086`、`1069…` 等；`"0001"` 生效为 `"1"`，拦掉**所有 1 开头号码**。
- 现有 `list.rs` 测试（`:242-268`）无一使用前导零前缀，故未被钉住。

**影响**：用户一个"看起来合法"的规则会静默锁死大片号码的通话与短信——正是该守卫设立的目的被绕过。

**建议修复**：长度守卫改在**归一化后**的 digits 上校验（或在 `add` 时就 `trim_zeros` 后判长），保证"校验的单位"与"匹配的单位"一致。这是本仓高频缺陷族"同一字段两种单位/两个读者"的又一实例。

**验收**：新增否定控制——`"010"` 与 `"0001"` 必须被 `add` 拒绝（或生效前缀仍为 3 位有效数字）；新增正控制——`"138"` 仍合法并只匹配 `138` 开头。

**状态：已修复（2026-09-25，REQ-A1561 ∕ F-TEL-035）**。`rule.rs` 新增 `effective_prefix`（暴露匹配所用的 `trim_zeros` 归一化），`Blocklist::add` 的长度守卫改判 `effective_prefix(&digits).len()`，与匹配同单位。`cargo test -p amos-blocklist` **16 ∕ 16**；新例 `a_leading_zero_prefix_that_normalizes_to_a_short_one_is_refused` 红先可复现（还原守卫 ⇒ `list.rs:321` 恰 1 红），另有 `prefix_match_still_tolerates_a_country_code_on_the_address` 钉住地址侧国家码容忍未误伤。

### PH-P0-5 · 拦截：冷启动来电筛选路径未加载 native 库 → 静默放行所有来电

**证据**：
- `android-glue/.../BlocklistGlue.kt:185-190` —— `mustRejectCall` 捕获 `Throwable` 后 **fail-open 返回 false**。
- 全仓 7 处 `System.loadLibrary("amos_tauri_lib")` 均在 UI 可达的胶水类（`CameraGlue`、`ClipboardGlue`、`NfcGlue`、`SensorGlue`、`BiometricGlue`、`BluetoothGattGlue`、`FlashlightGlue`）；
  `AmosCallScreeningService`、`SmsReceiver`、`BlocklistGlue` **均无加载**（唯一加载点是 `gen/.../Rust.kt` 的 init，由 Activity 触发）。
- `BlocklistGlue.kt:5-7` 与 `crates/amos-tauri/src/blocklist.rs:9-11` 的设计说明明确指出：系统可能**仅为筛一通来电而冷启进程**——正是未加载 native 的场景。

**影响**：服务/接收器单独冷启动时，JNI 调用抛 `UnsatisfiedLinkError` → 被 catch → **每个来电都被放行**，只留一行 `Log.w`。安全关键功能在点名场景下静默失效。

**建议修复**：在 `AmosCallScreeningService`（及 `SmsReceiver`）的静态初始化块中显式 `System.loadLibrary("amos_tauri_lib")`，并让加载失败**可观测**（例如回落到 fail-closed 或写入系统日志之外的审计槽）；`bind` 前必须先保证库就绪。

**验收**：新增 Kotlin 测试或仪器测试证明"仅服务启动的进程"也能完成一次 JNI 规则查询；`mustRejectCall` 在 native 不可用时不得静默返回 false 而不留痕。

**状态：已修复（2026-09-25，REQ-A1569 ∕ F-TEL-036）**。修法把 `init { System.loadLibrary("amos_tauri_lib") }` 加在两个**冷启动可达的 glue 对象**（`BlocklistGlue.kt`、`SmsGlue.kt`）上，而不是服务/接收器本身——二者都是 `object`，系统拉起进程后第一句 `bind`/`onSmsReceived` 即触碰对象、触发 `init`，效果等价，且与仓内 7 个姊妹胶水类同形（它们也把加载放在自己的 `init` 里）。Rust 侧新增源码钉 `every_cold_start_reachable_glue_loads_the_native_library_in_its_init_block`（`crates/amos-tauri/src/blocklist.rs`），把"规则一次说清、枚举全部入口"钉在 `include_str!` 的 Kotlin 源码上；负控证明删除任一处的加载都会让该钉转红。**边界**：本轮只消除"从不尝试加载"；库真加载失败时仍 fail-open（不静默拦掉所有来电），真机冷启动端到端复核不在本轮边界内。

### PH-P0-6 · 电话"录音"能力缺失（当前为诚实拒绝，非假功能）

**现象**：用户要求的"拨号→通话→**录音**→挂断闭环"中，录音环不存在。

## 7. 实测确认的优势（避免只报忧）

- **拒绝语义普遍诚实**：`RealCallRoute` 拒绝时报错而非 `unwrap_or(false)`；前端读 `bridgeDiag` 而非命令返回值。
- **枚举不向上取整**：`BackendKind`、`DialerRoleStatus`、"未知"从不折成"真实/已授权"。
- **短信前台门禁**三处读取全覆盖，且有钉住正反两向的测试。
- **拦截列表/线程/角标**复用**同一** `filter_threads`，无副本漂移。
- **邮件 `lettre` 确实校验 SMTP 回应码**（`smtp.rs:131`），非"没抛异常就算成功"；IMAP 用 `BODY.PEEK`、标志解析防伪造。
- **联系人 vCard 3.0** 折叠按八位字节、解析器全函数不抛、导入计数如实。
- **拦截规则引擎**为纯函数、无 I/O、14 个 crate 测试含否定控制、封顶存储+确定性淘汰。
- **录音与 SOS 的正确诚实边界**：录音在 UI 与 enums 层面如实报 `Failed`；紧急号在 provider 与 Kotlin 双重拒绝。
- **文档与代码能力一致**：`docs/sms.md`、`docs/telephony.md §10.5` 未发现夸大。
