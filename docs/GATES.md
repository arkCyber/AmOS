# The gates: what this repository checks, and which instrument answers which question

**Read this before writing a new instrument** (REQ-A483). Nothing here is a new mechanism — every
row is a script that already runs as part of `make lint`, `make test`, `make check`, the frontend's
`bun run check`, or a documented manual entry point. What was missing was the **index**: the set
lived in ~600 lines of `Makefile` comments, so the only ways to learn it were to read the whole
build or to write a gate that already existed. Two consecutive rounds of this session did the
latter — a Rust module-level orphan pass the frontend had had all along (REQ-A480), and a
hand-written sweep for "a `#[tauri::command]` no screen calls" that `tauri-command-scan.mjs` already
answers (REQ-A483) — which is the defect this page closes.

How to use it:

* **Coverage claims name a row.** "X is covered" is only meaningful with the instrument that
  answers it. If no row answers the question, the honest statement is "no instrument covers X".
* **New instrument ⇒ new row.** `node scripts/gate-index-scan.mjs` fails when a script under
  `scripts/` or `crates/amos-tauri/frontend-ts/scripts/` has no row here, or when a row names a
  script that does not exist. `--emit` drafts the row from the script's own header.
* **The wording is the script's own.** The "question" column quotes each script's header comment
  (its first sentence), so the index cannot drift into a flattering paraphrase; the header is where
  the *why* lives (what was measured, what was wrong before).
* **`failure` is derived, not authoritative.** It is read off each script's failure signals
  (`process.exit(<non-zero>)`, `exitCode =`, `throw`, or a read of a `*-baseline.json` /
  `*-allowlist.json`): **ratchet** = the current backlog is frozen in a baseline/allowlist and only
  *new* findings fail, **hard** = it can fail the run outright, **prints** = it reports and exits 0.
  Where this column and the script's own header disagree, the header wins — it is a reading aid,
  not a claim.

`gate-index-scan.mjs` itself is in the table (its first draft is checked by the same gate that
checks every other row). The corpus is deliberately **the same one `unwired-script-scan.mjs`
protects** — `scripts/*.{sh,mjs,js,cjs}`, the repository root `*.sh`, and the frontend's
`scripts/*.{sh,mjs,js,cjs}` — because the two gates answer one question each about one set: *is it
wired?* (that gate) and *is it in the index?* (this page's gate). A script that passes one and fails
the other is a trap for the next reader.

The **shell entry points** (`deploy.sh`, `dev.sh`, `gui-smoke-check.sh`, the Android bring-up
scripts …) are in the table for the same reason: they are instruments too, they were the first
finding of the wiring gate (REQ-A189), and "which script do I run for X?" is exactly the question
this page exists to answer.

## A suite's own verdicts: which clock they run on (REQ-A1154 / F-DEV-137)

The table above lists the instruments. An instrument's verdict is only worth what its *inputs* are
worth, and for a test the input is a clock. `frontend-ts/src/lib/__tests__/debounce.test.ts` ran
entirely on real timers — Bun has no `advanceTimersByTime`, the file's own header says so — so every
assertion was "sleep, then look", and the sleeps were 20 ms and 60 ms around a **50 ms** debounce.
`debounceLeading 应该防抖后续调用` asserted that two `wait(20)` calls still land inside the window:
a **10 ms** margin. In the 3 915-case batch — the run `bun run check` actually performs — the two
sleeps summed past 50 ms, the third call executed immediately, and 「仍然只有第一次」 became
`Received number of calls: 2`. The file passed **20/20 alone** and failed **2/2** in the batch. The
same family of margins ran through the whole file (5 ms in the delay case, 5–20 ms in eleven
others), so no single case was "the flaky one".

Two rules now make each verdict load-independent, and they are worth stating as the shape to reach
for whenever a test's verdict is decided by a clock:

- **The arrival window** ("it must have fired") stops guessing a duration and polls the event
  itself (`waitFor(cond, timeout)`). The criterion is the event; the timeout is only a backstop so a
  never-arriving event cannot hang the suite.
- **The hold window** ("it must not have fired yet") cannot be polled — it is genuinely a claim
  about a duration — so the debounce interval was raised to 200 ms (long-delay 400, autosave 320)
  while the sleeps stayed small. Every such verdict now has ≥ 140 ms of margin, an order of
  magnitude more than the scheduling jitter that used to decide it.

Test names and the semantics each one pins are unchanged; no production code was touched. Honest
limits: these are still real timers — the margin was raised, the clock was not virtualised (Bun does
not offer one) — and the file's runtime went from 1.8 s to ~5.2 s, the price paid for a verdict that
does not depend on how busy the machine is. Negative controls: removing `debounce`'s timer reset
reddens exactly the four debouncing cases (4 red / 16 green); folding `debounceLeading`'s window
predicate to `if (true)` reddens exactly the two leading-edge cases (2 red / 18 green); both
restored byte-identically (`debounce.ts` = `749ff589…`).
